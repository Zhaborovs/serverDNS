# Руководство по развертыванию кластера Combain-Mesh

> Навигация: [Главная (README)](../README.md) · [Архитектура стека](architecture.md) · [Быстрый старт для клиентов](quickstart_clients.md) · [VK / Yandex CDN (белые списки)](cdn_whitelist_guide.md) · [FAQ и диагностика](faq_troubleshooting.md)

**Combain-Mesh** — децентрализованная P2P-сеть управления поверх приватного WireGuard-туннеля (`wg-mesh0`, `10.99.0.0/24`) для связки **2–3 зарубежных exit-нод** (DE / NL / FI) и **1 российского ретранслятора** (`ru_relay`).

Ключевые возможности:
- **Без единой точки отказа (No Single Master):** каждая нода хранит локальную SQLite-базу (`/etc/server-combain/mesh.db`) с LWW-синхронизацией (Last-Write-Wins) и обменивается дельтами каждые **15 секунд** по HMAC-SHA256 API (`22777/tcp` строго на `lo` и `wg-mesh0`).
- **Подключение в 1 строку (`combain-join://`):** новый сервер присоединяется к кластеру одним инвайт-токеном — без ручного копирования `MESH_SECRET`, IP-адресов и ключей существующих пиров.
- **Авто-роль по GeoIP и удалённая смена ролей:** при инициализации и подключении роль определяется автоматически (`RU` -> `ru_relay`, зарубежный IP -> `exit`), а переключить роль любого узла (`exit <-> ru_relay`) можно с любого живого сервера кластера через LWW-синхронизацию.
- **Автоматический failover и IPv6-каскад:** при недоступности ноды более **45 секунд** она помечается `offline` и исключается из подписок (`/u/`, `/u-json/`, `/api/v1/client/bootstrap`) и цели каскада (`mesh_cascade_target.json`). Для нод с IPv6 автоматически формируются резервные `-IPv6` профили.
- **Синхронное обновление всего кластера:** одна команда `comb update --cluster` обновляет текущий сервер и отправляет HMAC-подписанный сигнал `POST /mesh/update` на все онлайн-ноды.
- **Персональные подписки для семьи и друзей:** лимит устройств (`max_devices` по `X-HWID`), срок действия (`expires_at`), мгновенное отключение/продление и встроенный двухуровневый RU-обход (Госуслуги, MAX, банки — `direct`, SDK-телеметрия — `block`).

## 1. Архитектура и распределение IP в кластере

Рекомендуемая схема адресации в подсети `10.99.0.0/24` (порт WireGuard `51829/udp`):

| Нода | Роль (`MESH_ROLE`) | Mesh IP (`wg-mesh0`) | Публичный IPv4 / IPv6 (пример) | Назначение |
| :--- | :--- | :--- | :--- | :--- |
| `de-1` | `exit` | `10.99.0.1` | `203.0.113.10` / `2001:db8::1` | Основной зарубежный выход (Германия) |
| `nl-1` | `exit` | `10.99.0.2` | `203.0.113.20` / `2001:db8::2` | Резервный зарубежный выход (Нидерланды) |
| `fi-1` | `exit` | `10.99.0.3` | `203.0.113.30` | Дополнительный выход (Финляндия, опционально) |
| `ru-msk-1` | `ru_relay` | `10.99.0.10` | `198.51.100.10` | Российский ретранслятор (входная точка и каскад на `exit`) |

> **Безопасность фаервола (`COMBAIN-PROTECT`):** Модуль `10_mesh_cluster.sh` добавляет правила строго в изолированную цепочку `COMBAIN-PROTECT` (не сбрасывая `iptables` и не затрагивая Docker): `51829/udp` открыт для WireGuard, а порт API `22777/tcp` разрешён **только** на `lo` и `wg-mesh0` (снаружи полностью закрыт правилом `DROP`).

## 2. Быстрое развертывание кластера (через 1-строчный инвайт-токен)

### Шаг 1. Базовая установка на каждом сервере

На каждом сервере (`de-1`, `nl-1`, `ru-msk-1`) выполните стандартную установку Server-Combain:

```bash
comb install
```

*(Команды `comb` и `combain` — взаимозаменяемые алиасы.)*

### Шаг 2. Инициализация первой ноды (`de-1`) с GeoIP авто-ролью

1. Откройте меню кластера:
   ```bash
   comb mesh
   ```
   *(или пункт `9` в главном меню `comb`).*
2. Выберите **`1) Инициализировать эту ноду (авто-роль по GeoIP: RU -> ru_relay, иначе -> exit)`**:
   - **Роль ноды:** нажмите `Enter` (`0` = `auto`). Скрипт автоматически определит страну внешнего IP через GeoIP (`ipinfo.io` / `ifconfig.co`): для `RU` назначит `ru_relay`, для зарубежных серверов — `exit`, а также сохранит код страны для флагов в клиентских подписках.
   - **Имя ноды:** `de-1`.
   - **Mesh IP:** `10.99.0.1` (для `ru_relay` по умолчанию предлагается `10.99.0.10`).
   - **Порты:** WG `51829/udp`, API `22777/tcp` (по умолчанию).
   - **`MESH_SECRET`:** нажмите `Enter` для автоматической генерации 32-символьного ключа.
3. Нода автоматически поднимет `wg-mesh0`, применит правила `COMBAIN-PROTECT`, зарегистрирует свой IPv4 и (при наличии) `public_ipv6` и запустит `combain-mesh.service`.

### Шаг 3. Генерация инвайт-токена в 1 строку на ноде A (`de-1`)

В меню `comb mesh` выберите **`2) Выдать инвайт-токен в 1 строку (для подключения нового сервера)`**.

Скрипт выведет компактную строку вида:

```text
combain-join://eyJ2IjoxLCJzZWNyZXQiOiIuLi4iLCJhc3NpZ25lZF9tZXNoX2lwIjoiMTAuOTkuMC4yIiwiYXBpX3BvcnQiOjIyNzc3LCJwZWVycyI6W119
```

Внутри токена (Base64URL JSON) уже упакованы:
- общий секрет кластера `MESH_SECRET`;
- автоматически выделенный свободный `assigned_mesh_ip` (`10.99.0.2`, `.3` и т. д.);
- порт API (`22777`);
- список всех текущих нод кластера (их `public_ip`, `mesh_ip`, `wg_port` и `wg_pubkey`).

### Шаг 4. Подключение новой ноды B (`nl-1` или `ru-msk-1`) одной вставкой

На новом сервере откройте `comb mesh` и выберите **`3) Подключиться к кластеру по инвайт-токену (combain-join://...)`**:

1. Вставьте строку `combain-join://...`.
2. Задайте имя ноды (например `nl-1` или `ru-msk-1`).
3. Для роли нажмите `Enter` (`auto` — GeoIP сам выставит `exit` для Нидерландов и `ru_relay` для РФ).
4. Нода автоматически:
   - настроит `wg-mesh0` с выданным `assigned_mesh_ip` и применит фаервол `COMBAIN-PROTECT`;
   - добавит всех существующих пиров из инвайта в `wg-mesh0` и `mesh.db`;
   - запустит `combain-mesh.service` и выполнит `sync-now`.
5. **Завершающий шаг WireGuard:** в конце скрипт выведет `WG PubKey` новой ноды. Поскольку WireGuard требует взаимного доверия пиров, добавьте новую ноду на уже работающих серверах через пункт **`8) Ручное подключение пира (Join Peer) / карточка ноды`** (достаточно один раз для каждой пары).

### Шаг 5. Проверка статуса кластера

В меню `comb mesh` выберите **`6) Статус кластера, нод и wg-mesh0 (node-list + cascade-target)`**:
- в `wg show wg-mesh0` у каждого пира должно отображаться `latest handshake`;
- в `node-list` все серверы должны быть в статусе `online`;
- строка `Active cascade exit` покажет выбранную здоровую зарубежную `exit`-ноду для каскада.

> Если требуется принудительно прогнать синхронизацию прямо сейчас, используйте пункт **`7) Принудительная синхронизация кластера сейчас (sync-now)`**.

## 3. Удалённая смена ролей (LWW) и IPv6-каскад `RU-Relay -> Exit`

### Удалённая смена роли любого узла (`exit <-> ru_relay`)

Менять роль можно **с любого живого сервера кластера** — правка автоматически реплицируется по LWW на все ноды:

1. В `comb mesh` выберите **`4) Сменить роль любого узла в кластере (exit <-> ru_relay с любого сервера)`**.
2. Введите имя (или `node_id`) узла и новую роль: `exit` или `ru_relay`.
3. То же самое через CLI:
   ```bash
   python3 /opt/server-combain/scripts/mesh/combain_mesh.py node-set-role \
     --state-dir /etc/server-combain --node ru-msk-1 --role ru_relay
   ```

При следующем цикле синхронизации (или немедленно через push) все ноды обновят `mesh.db` и файл цели каскада `/etc/server-combain/mesh_cascade_target.json`.

### Настройка каскада `RU-Relay -> Exit` и поддержка IPv6

На российской ноде (`ru-msk-1`) выберите `comb mesh` -> **`9) Настройка каскада RU-Relay -> Exit поверх wg-mesh0`**:
- Модуль сгенерирует готовый JSON-шаблон `/etc/server-combain/mesh/ru_relay_cascade.json` для маршрутизации клиентского трафика с российской точки входа (`443/tcp`) на зарубежную `exit`-ноду (например `10.99.0.1:443`) поверх зашифрованного `wg-mesh0`, с прямым выходом (`direct-ru`) для Госуслуг, MAX, VK и банков РФ.
- **Авто-выбор цели каскада:** демон `combain-mesh` постоянно отслеживает здоровье `exit`-нод и записывает лучшую доступную цель в `mesh_cascade_target.json` (просмотр: пункт `6` / команда `cascade-target`).
- **IPv6-каскад и dual-stack в подписках:** если на `exit`-ноде или ретрансляторе обнаружен глобальный IPv6 (`SERVER_IPV6`, например `2001:db8::1`), он сохраняется в `mesh.db` при `init-node` (`--public-ipv6`). Генератор подписок (`/u/` и `/u-json/`) автоматически добавляет для таких нод отдельные `-IPv6` профили (`Combain-Direct-XHTTP-IPv6`, `Combain-Direct-WS-IPv6`) с тем же `SNI` домена — клиенты получают резервный маршрут по IPv6 на случай фильтрации IPv4.

## 4. Плейбук смены IP и отказоустойчивости (Reg.ru `TTL=300`)

Чтобы блокировка IP-адреса одной из нод не оставила семью и друзей без доступа, заранее настройте DNS и следуйте простому регламенту.

### Предварительная настройка DNS (Reg.ru / любой регистратор)

Для всех доменов кластера (`de.vpn.example.com`, `nl.vpn.example.com`, `dns.vpn.example.com`) выставите минимальный **TTL = `300` секунд (5 минут)** на `A`-записях (и `AAAA`, если используется IPv6).

| Запись | Тип | Значение (пример) | TTL |
| :--- | :--- | :--- | :--- |
| `de.vpn.example.com` | `A` | `203.0.113.10` | **`300`** |
| `dns.vpn.example.com` | `A` | `203.0.113.10` | **`300`** |
| `nl.vpn.example.com` | `A` | `203.0.113.20` | **`300`** |

> **Зачем нужен `TTL=300`?** При стандартном TTL (3600–86400 с) кэш провайдерских DNS в РФ держит старый заблокированный IP часами. С `TTL=300` переключение домена на новый IP происходит в пределах **5 минут** без перевыпуска клиентских подписок.

### Сценарий A: Хостер выдал новый IP на том же сервере

1. Подключитесь к серверу и запустите мастер быстрой смены IP:
   ```bash
   comb change-ip
   ```
   *(или пункт `2` в главном меню `comb`).*
   Мастер автоматически определит новый внешний IPv4, обновит `state.env`, перепишет правила `AdGuardHome.yaml` (при остановленном сервисе), обновит `Endpoint` в профилях AmneziaWG, перезапустит `sniproxy` и пересоберёт подписки.
2. В панели Reg.ru замените IP в `A`-записи домена на новый (с `TTL=300` клиенты увидят новый IP через ≤5 минут).
3. Если изменился внешний IP ноды, обновите её `Endpoint` в `/etc/wireguard/wg-mesh0.conf` на соседних нодах (или повторно добавьте через `comb mesh` -> пункт `8`) и выполните `sync-now` (пункт `7`).

### Сценарий B: VPS полностью недоступен или заблокирован (мгновенный failover + замена ноды)

1. **Автоматический failover (≤45 сек):** пока вы разбираетесь с хостером, остальные ноды кластера пометят упавший сервер `offline` через 45 секунд. Клиентские подписки (`/u-json/` и массив `mirrors` в `/api/v1/client/bootstrap`) автоматически исключат его и продолжат работать через оставшиеся здоровые `exit`-ноды.
2. **Подъём замены:** арендуйте новый VPS, выполните `comb install`, сгенерируйте 1-строчный токен `combain-join://...` на любой живой ноде (`comb mesh` -> пункт `2`) и подключите новый сервер (`comb mesh` -> пункт `3`).
3. **Переключение DNS:** обновите `A`-запись домена (с `TTL=300`) на IP новой ноды. Все пользователи и их `sub_token` автоматически подтянутся через LWW-синхронизацию — заново раздавать ссылки семье не нужно.

## 5. Синхронное обновление всего кластера

Обновить код Server-Combain и переприменить конфигурации (`Nginx`, `AdGuard Home`, `sniproxy`, `3x-ui`, подписки и `combain-mesh`) сразу на всех серверах кластера можно одной командой с любой ноды:

```bash
comb update --cluster
```

Также доступно через интерактивное меню **`comb service`** (или пункт **`10`** главного меню `comb`):
- **`1) Обновить ЭТОТ сервер`** (`comb update`) — выполняет `git pull --ff-only`, доопределяет IPv6/страну, перерендеривает Nginx, синхронизирует AdGuard (гео-домены + RU-телеметрия) и `sniproxy`, обновляет инбаунды `3x-ui`, подписки и перезапускает `combain-mesh`.
- **`2) Синхронно обновить ВЕСЬ кластер Combain-Mesh`** (`comb update --cluster`) — обновляет локальный сервер и рассылает HMAC-подписанный запрос `POST /mesh/update` на все онлайн-ноды кластера по `wg-mesh0`.
- **`3) Обновить Docker-образы`** — подтягивает свежие образы `Nginx`, `3x-ui`, `MTProto`, `SOCKS5`.
- **`4) Статус всех служб, контейнеров и портов`** — сводная диагностика состояния ноды.

## 6. Выдача подписок семье и друзьям

Создавать и редактировать пользователей можно на **любой** ноде кластера — изменения синхронизируются на все серверы автоматически и применяются в локальной базе `/etc/x-ui/x-ui.db`:

1. Выполните `comb mesh` -> **`5) Пользователи и подписки`** -> **`1) Создать пользователя`**.
2. Укажите:
   - имя латиницей (например `mama`, `alex`);
   - лимит устройств (`max_devices` по HWID, по умолчанию `3`);
   - срок действия в днях (`30`, `90` или `0` для бессрочного доступа);
   - заметку (опционально).
3. Модуль выдаст персональные ссылки и QR-код:
   - **Base64 URI (универсальная):** `https://de.vpn.example.com/u/<sub_token>`
   - **Xray JSON (рекомендуется для v2RayTun / Happ, включает RU-обход и 10–25B SNI Split):** `https://de.vpn.example.com/u-json/<sub_token>`
   - **Bootstrap API (для фирменного приложения):** `https://de.vpn.example.com/api/v1/client/bootstrap` + заголовок `X-Sub-Token: <sub_token>`

Подписки `/u/` и `/u-json/` автоматически передают клиентским приложениям стандартные заголовки: `profile-title`, `profile-update-interval: 6`, `subscription-userinfo` (с датой `expire`) и `announce` с подсказкой об исключении MAX, Госуслуг и банков.

### Управление доступом (подменю `5`)
- **Список пользователей (`2`):** показывает статус (`enabled` / `disabled`), число занятых устройств (`used/max`), дату окончания и токен.
- **Продление срока (`3`, `user-extend`):** добавляет дни к текущей дате окончания.
- **Сброс HWID (`4`, `user-reset-devices`):** очищает привязанные устройства (если человек сменил телефон или ПК).
- **Отключение / включение (`5` / `6`, `user-disable` / `user-enable`):** мгновенно блокирует подписку и удаляет UUID пользователя из `3x-ui` на всех нодах кластера.

## 7. Контракт `/api/v1/client/bootstrap` (интеграция клиентского приложения)

Клиентское приложение подключается к **любому** домену из кластера (`mirrors`) по HTTPS на `443/tcp` (Nginx проксирует запрос на локальный `127.0.0.1:22777`):

### Запрос

```http
GET /api/v1/client/bootstrap HTTP/2
Host: de.vpn.example.com
X-Sub-Token: <персональный_sub_token_пользователя>
X-HWID: <уникальный_идентификатор_устройства>
```

*(Также поддерживается передача через query-параметры `?token=<sub_token>&hwid=<hwid>`.)*

### Успешный ответ (`200 OK`)

```json
{
  "account": {
    "username": "alex",
    "expires_at": 1798761600000,
    "max_devices": 3,
    "used_devices": 1,
    "enabled": true
  },
  "smart_dns": [
    {
      "node_id": "node-de-1",
      "name": "de-1",
      "role": "exit",
      "doh": "https://dns.vpn.example.com/dns-query",
      "dot": "tls://dns.vpn.example.com",
      "ip": "203.0.113.10"
    }
  ],
  "mirrors": [
    "https://de.vpn.example.com",
    "https://nl.vpn.example.com"
  ],
  "sub_url": "https://de.vpn.example.com/u/<sub_token>",
  "sub_json_url": "https://de.vpn.example.com/u-json/<sub_token>"
}
```

*(Поле `expires_at` возвращается в миллисекундах Unix epoch; `0` означает бессрочный доступ.)*

### Обработка кодов ответа в приложении

- **`200 OK`:** сохранить массив `mirrors` (резервные домены для обхода блокировки основного домена), применить `smart_dns` и загрузить актуальный мульти-нодовый конфиг по `sub_json_url` (передавая `X-HWID`).
- **`401 Unauthorized`:** отсутствует `X-Sub-Token` (`{"error": "missing_token"}`).
- **`403 Forbidden`:** подписка отключена (`user_disabled`), истёк срок (`user_expired`) либо превышен лимит устройств (`device_limit_exceeded` с полями `max_devices` и `used_devices`).
- **`404 Not Found`:** неверный `sub_token` (`{"error": "user_not_found"}`).
- **Таймаут / сетевая ошибка:** автоматически повторить `GET /api/v1/client/bootstrap` на следующем домене из кэшированного массива `mirrors`.
